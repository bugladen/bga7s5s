# Lodestone (_03065) — create-faction-attachment

## Orientation
Eddie asked to finish `_03065` via create-faction-attachment, and specifically to use a **condition** for the restriction (same request shape as Harpoon yesterday).

## Text
- Passive: Opponent's abilities cannot move the equipped character Home.
- City Action: Sink this card • Move your performer Home.

## Classification
- Passive restriction → condition stamp (not Pattern A equip gate)
- Pattern C AttachmentAction (City Action, `cardInCity` gate, no picker state)

## WHY condition for the restriction
Mirrored Harpoon `_03064` / Soline / Indomitable Will:
1. Tooltip shows the string for free (conditions list + Started/Ended notifs)
2. `Character::eventCheck` gates on `hasCondition` — works even if Lodestone leaves `$theah->cards` mid-resolve (e.g. during its own sink)
3. Clear on unequip restores cleanly

Alternatives considered:
- Attachment-only `eventCheck` on EventCardMoving: dies if Lodestone is mid-sink / not in world
- Flag on the Action class: worse for tooltip / orphaned state
- Blocking all Home moves: wrong — own abilities (incl. Lodestone City Action) must work

## Opponent detection
`EventCardMoving.initiatingPlayerId` is unreliable — `Maneuver_01033` sets it to the **victim**. Gate uses `sourceId` → source card `ControllerId != character.ControllerId`. Own City Action uses attachment as source (same ControllerId) → allowed.

## City Action
No choose state — sink + move resolve on `EventActionTriggered`.
Sink chain mirrors `Technique_02055` (Dame of Swords): unequip → removeFromPlay → `createCardAddedToFactionDeckEvent(..., false)`.
Move uses `engage=false` (sink is the cost, not engage).

## Enforcement extras
- `Character::eventCheck` for all opponent Home moves while condition present
- `Maneuver_01033` activate-time Lodestone check (same WHY as Harpoon activate-time — queued move would soft-fail via `queueEvent` swallowing UserException)
