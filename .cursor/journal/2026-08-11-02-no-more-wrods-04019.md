## Orientation
Continued bas Eisen Risk work after Seek Each Devil `_04018`. User asked to finish `_04019` via create-risk.

## Text → patterns
Single clause: **En Garde Action: Engage Melee Weapon or Eisenfaust on performer • They issue [Combat] challenge to target opposing character.**

- Pattern B (`RiskAction`) + En Garde `!$Engaged` precondition (not performer Engage cost).
- Engage cost on attachment — mirror `Action_02020` attachment filter (`Weapon`+`Melee` OR `Eisenfaust`, unengaged).
- Challenge half mirror `Action_01083` / `Action_03058`: performer issues Combat → `NORMAL_CHALLENGE_TYPE` (auto-engage performer on issue is OK; attachment was separate printed Engage cost).
- Printed **"target opposing character"** → Cesca `IAbilityThatTargetsCharacters` / `IRiskThatTargetsCharacters`.

## Flow
1. `EventActionTriggered` → `"04019"` attachment-chooser GameState (buttons like Yield `02020_2`).
2. On attachment confirm: `createCardEngagedEvent` on attachment → set `CHALLENGE_STAT`/`CHALLENGE_TYPE` → transition `"04019_2"` → shared `HIGH_DRAMA_CHALLENGE_ACTION_CHOOSE_TARGET`.
3. Target validated via `isValidTargetForAbility`; challenge resolves elsewhere (`createActionResolvedEvent` comment).

## WHY not target-first like Yield
Printed bullet order is Engage attachment **then** challenge. Yield (`02020`) picks target first for UX because both steps are on one City Action with opponent response — different shape.

## WHY "They" = performer for challenge plumbing
Attachments don't issue challenges in engine; engaged weapon is the cost, performer is `CHOSEN_PERFORMER` for challenge pipeline (same as other "your performer issues" Actions).
