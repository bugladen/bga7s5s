# Arson (_02007) Card Audit

## Context

Continuing the pattern of card audits for the TAC expansion. Previous audits: Elisabetta Bonora (02002), Mourad (02003). Eddie clarified notation: bullet `•` separates cost from effect; "available" means uncontrolled.

## What I Found

Three bugs in `Action_02007.php`, all related to the "target" keyword in the card text — the action didn't properly enforce that valid targets must exist.

### Bug 1 & 2: No target validation in availability/performer checks
`isAvailableToPlayer` checked for Red Hand characters in the city but never verified any of them were at locations where the effect could do something. `getPerformersForAction` had the same gap. A player could select a Red Hand performer at a location with no renown and no available cards, pay the cost (wound), and get nothing.

Fixed to check: renown > 0 OR available (uncontrolled) City cards at the performer's location. This is an OR condition — Eddie clarified the effect is "do as much as you can", so either half being possible is enough.

This follows the same pattern as Action_02010 (Strega wound transfer), which carefully validates that performers are at locations where the effect can actually be carried out.

### Bug 3: Missing `isControlled()` server-side validation
`actFromActionWithId` validated the card existed and was at the right location, but didn't check `!$card->isControlled()`. Same category of security bug as was found in 02002's missing top-3 validation — the client could submit any card ID and bypass the intended filtering.

## Decisions

- The `else` branch in `handleEvent` is a legitimate code path, not just defensive. A performer can be selected because their location has renown > 0 but no available cards. In that case: wound (cost), remove renown (effect), skip discard (no targets). This correctly implements "do as much as you can".
- WHY the condition is OR not AND: Eddie clarified this. The effect text "Remove a Renown and discard target available City card" uses "and" to list two effects, but the action should be performable if either effect can be carried out. You don't need both renown AND cards — either is sufficient to make the action worthwhile after paying the wound cost.

## Pattern Notes for Future Audits

When a card says "target X", both `isAvailableToPlayer` AND `getPerformersForAction` should validate that valid targets exist. And `actFromActionWithId` must always re-validate the server-side constraints that the UI enforces — never trust the client.
