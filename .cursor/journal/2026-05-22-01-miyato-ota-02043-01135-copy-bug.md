# Miyato and Ota (02043a) — Copying Maneuvers with state transitions

## The Bug (initial scope)

`Technique_02043a` copies the most recently performed maneuver onto a clone owned by Miyato/Ota and queues `EventResolveManeuver` for the clone's unique ID. For most state-transitioning maneuvers (e.g. Maneuver_02038, Maneuver_01051), the transition is fired from `EventResolveManeuver`, so the copy works.

`Maneuver_01135` (Mireli's Revision) is the *only* state-transitioning maneuver that fires its transition from `EventManeuverActivated` rather than `EventResolveManeuver` — see the 2026-04-02 journal for why (deliberate ordering so the choice state runs before Reaction_01146b's cancel transition).

Result: the technique never fired `EventManeuverActivated` for the clone, so the clone's transition handler never ran, and `duelResolveManeuver_01135` was never entered.

Even after fixing the firing-side, the clone's transition (`"01135"`, fired via `stackEvent` inside the technique-events processor) had no matching transition in `DUEL_CHOOSE_TECHNIQUE_EVENTS`, so `nextState("01135")` would have thrown.

## Final design — minimal

Only two kinds of changes are needed:

### 1. Add the maneuver transition names to `DUEL_CHOOSE_TECHNIQUE_EVENTS` (states.inc.php)

```php
"01133" => States::DUEL_RESOLVE_MANEUVER_01133,
"01135" => States::DUEL_RESOLVE_MANEUVER_01135,
"01142" => States::DUEL_RESOLVE_MANEUVER_01142,
"01164" => States::DUEL_RESOLVE_MANEUVER_01164,
"01165" => States::DUEL_RESOLVE_MANEUVER_01165,
"02057" => States::DUEL_RESOLVE_MANEUVER_02057,
```

When a clone's transition event fires inside `stRunEvents` running in `DUEL_CHOOSE_TECHNIQUE_EVENTS`, `runEvents` calls `nextState("01135")` (or whichever) — that name must be a registered transition on the current state.

### 2. For 01135 specifically — fire `EventManeuverActivated` for the clone

`Technique_02043a.php` now queues `EventManeuverActivated` for the clone before `EventResolveManeuver`. Required only for 01135, but harmless for the other state-transitioning maneuvers (their handlers match on Resolve and the clone's Activated only matches the clone's own ID; reactions that fire on Activated either already used their slot or get a legitimate second activation to react to).

### 3. Also queue `EventDuelCalculateManeuverValues` for the clone

After ResolveManeuver, queue CalcManeuverValues for the clone too. Mirrors the normal flow (`stResolveManeuverFromCombatCard` queues Activated → Resolve → Calc). Lets the clone's own choice contribute to combat values via the maneuver channel — without this, stateful maneuvers like 01135 where the clone's choice (+2 Parry vs wound) influences combat stats had no path for the clone's choice to apply.

(Note: this contradicts an earlier note in my 2026-04-06 journal that said NOT to fire CalcManeuverValues for the clone — Eddie corrected that. The original concern about triple-counting via mode-'maneuver' was either overstated or the underlying logic has since been fixed.)

### No `techniqueCopy` exit transitions needed

Initially added a `"techniqueCopy"` exit on each maneuver state plus owner-type detection in each maneuver's action method. **Reverted** — the natural return path already lands the right place:

1. Maneuver state exits `""` → `DUEL_RESOLVE_MANEUVER_EVENTS` (stRunEvents)
2. → `endOfEvents` → `DUEL_SET_NEXT_COMBAT_CARD`
3. `stSetNextCombatCard` checks `NEXT_COMBAT_CARD` global (deleted when last card was set) and `ROLL_THE_BONES_ACTIVATED` (also typically clear) — both are 0/false during Miyato's action-phase technique use → `noMoreCombatCards` → `DUEL_CHOOSE_ACTION`.

Same destination as the explicit techniqueCopy route. Adding extra transitions and per-maneuver detection logic was overengineering — relying on the state machine's existing recovery path is simpler and uniform across every state-transitioning maneuver. (Eddie spotted this; I had defaulted to "explicit is better" without checking that the implicit path already converges.)

## Firing `EventManeuverActivated` — the WHY

Queue Activated rather than special-casing Maneuver_01135 on Resolve because:
- Matches how `stResolveManeuverFromCombatCard` builds the normal flow (Activated → Resolve → Calc).
- Keeps the clone's lifecycle symmetric with the original.
- Means any future Activated-only handler also works for copy without revisiting the technique.

Side effect: opposing Reaction_01146b (Let The Sword Decide) sees the clone's Activated and can queue another cancel reaction. If 01146b is already used, `isAvailable()` blocks it. If unused, the opponent gets a chance to cancel the COPY — defensible game-rules-wise. `deleteManeuverEvents(clone.Id)` only catches events containing the clone ID, so the technique's CalcTechniqueValues and deferred locker send (which reference techniqueId not clone.Id) survive a clone cancel.

## Known Limitations Not Touched

- Maneuver_01135's +2 Parry choice on the clone doesn't add Parry independently — Maneuver_01135 applies +2 Parry via `EventDuelCalculateManeuverValues`, which the technique deliberately does not fire for the clone (per 2026-04-06 journal: would triple-count combat values). The technique already mirrors the original maneuver's stored values through the technique channel, so the clone-side choice on 01135 only affects the wound/next-round-thrust branch visibly.
- The clone is cleaned up at `EventDuelNewRound`. For 01135's `ReduceThrustNextRound`, that fires in the next round *via* `EventDuelCalculateCombatCardStats`, which happens after `EventDuelNewRound` — so the clone's next-round thrust reduction would be removed before it could apply. Pre-existing design quirk; not in scope.
- Maneuver_01133 (Matushka's Efficiency) implements `ISorcererAbility` and gates `isAvailableToPlayer` on the actor having the `Sorcerer` trait. Miyato isn't Sorcerer, so this copy path can only fire if the original 01133 was already validly performed by a Sorcerer earlier in the round. The clone's `EventManeuverActivated`/`EventResolveManeuver` are queued directly by the technique and don't re-check `isAvailableToPlayer`, so the copy proceeds — the SorcererAbilityStart/Played events will fire for Miyato. That may have side effects (corruption checks etc.) that haven't been audited. Flag for future review.
- Maneuver_01165 ("I Know That Trick!") pass case: when copied via tech and player passes, exits `"pass"` → `DUEL_RESOLVE_MANEUVER_EVENTS` (rather than tech-events). Same natural recovery as above — `endOfEvents` → `DUEL_SET_NEXT_COMBAT_CARD` → `noMoreCombatCards` → `DUEL_CHOOSE_ACTION`. Works.
- Other-faction state-transitioning maneuvers (01051, 01059, 01077, 01079, 01103, 01108, 01110, 01113, 01115, 02038) and the two `_2` continuation transitions are still latently broken if a future card lets non-Ussura/Neutral combat cards be copied by Miyato. Not in scope per user instruction.
