# Action_01028 CanBeClaimed Availability Gate

Eddie: Action_01028 needs to check `theah->canLocationBeClaimedBy` to be used.

## Context

Continuation of today's claim-gate sweep (01095a, 01130, 02029, 01075, 01080, 01126).
Resolve path already guarded claim emit with `canLocationBeClaimedBy` (EventLocationPressureResult).
Availability did not — Pack Tactics could still be played from hand when Leshiye / Indomitable
Will had blocked claims at every (or the intended) city location.

Unlike 01075 (fixed performer location), Pack Tactics lets the player choose any city
location. So "claimable" is an any-of check, not a single location.

## Changes

1. `getClaimableLocations()` — city locations where `canLocationBeClaimedBy($playerId, name)`.
2. `isAvailableToPlayer` — parent + at least one claimable location (Action_01086 pattern).
3. `getArgsFromAction` for state 01028 — pass `locationIds` so UI only offers claimable sites.
4. `actFromActionWithIds` — reject unclaimable choice with BgaUserException.
5. JS `highDramaPhase01028` — use `args.locationIds` + `getCityLocationElement` like 01086,
   instead of all `getListofAvailableCityLocationImages()`.

WHY gate at availability (not only resolve): pressure-then-claim is the point of the Risk;
playing it when no location can be claimed wastes the hand card / wealth cost.
WHY also filter UI + act: partial board (one location blocked) still allows the Risk —
player must not be able to pick the blocked location and burn the card for a notify-only miss.
WHY `canLocationBeClaimedBy` not `$location->CanBeClaimed`: central API, `$playerId`
reserved for future per-player rules. Resolve-time recheck kept (claimability can change mid-flow).
