# Move Along (01056) Audit

## Card Text
> **City Action:** Your performer issues a [Combat] challenge to target opposing character. They may move Home engaged. If they do, cancel the challenge.

## Audit Result: Two semantic concerns documented; no fixes applied

The implementation is a reasonable functional approximation but does not strictly match the card text's ordering. Both concerns require non-trivial restructuring and/or alignment with broader codebase conventions, so I'm leaving the code as-is and documenting the findings for the next pass.

## Implementation Walkthrough

**_01056.php** — Risk card (Eisen, 1 Wealth, Parry 1, Thrust 4, traits Challenge + Provocation), single Action_01056. ✓ Stats match expected layout.

**Action_01056.php** — Extends `RiskCityAction` implements `IAbilityThatTargetsCharacters`. Three-step flow:
1. State `HIGH_DRAMA_PLAYER_TURN_01056` — performer's controller picks target opposing character at performer's location (filtered via `canChallenge()` + opposing-at-location). On confirmation, queues transition to `01056_2` for defender's controller.
2. State `HIGH_DRAMA_PLAYER_TURN_01056_2` — defender's controller chooses **Move Home** (id=1) or **Continue with Challenge** (id=2).
   - **id=1**: queue `CardMovingEvent` to LOCATION_PLAYER_HOME with engage=true; resetPlayerPassCount; setUsed; queue `ActionResolvedEvent`.
   - **id=2**: set `CHALLENGE_STAT=Combat`, `CHALLENGE_TYPE=MOVE_ALONG_CHALLENGE_TYPE`; queue transition `01056_3` (mapped to `HIGH_DRAMA_CHALLENGE_ACTION_TECHNIQUE_AVAILABLE`) targeting performer's controller.
3. Standard challenge flow then runs technique-available → activate technique → setup challenge → `stIssueChallenge` (which actually fires `EventChallengeIssued`).

State registrations and JS button wiring are present and consistent.

## Concern 1: `EventChallengeIssued` is never fired in the Move-Home branch

**Card text says**: challenge is *issued first*, then defender may move home, *then* if they do, cancel the challenge.

**Implementation does**: defender's move-home choice is offered *before* the challenge is ever issued. If they pick move-home, `stIssueChallenge` is never reached, so `EventChallengeIssued` is never queued.

**Why it matters**: cards with "When X issues a challenge" reactions miss firing when the defender chooses move-home. Concrete examples:
- `Reaction_01065` (Henri) — "When Henri issues a challenge, engage his equipped Weapon": Henri's weapon never engages if Henri uses Move Along and the defender opts to go home.
- `Reaction_02012` (Turais) — "When Turais issues a challenge, wound him • En garde him": same issue.
- `Reaction_02037` — "After an opposing character issues a challenge • Equip this card to your character at this location": same issue.

Per the literal card text, "cancel the challenge" implies the challenge *was* issued and is then cancelled — at which point reactions to the issuance should already have resolved (engagement of Henri's weapon shouldn't be undone by the cancellation; the reactions ran on the issued event). Compare with how `CHALLENGE_CANCELLED` works in `stChallengeActionCheckCancelled` (StatesTrait.php:781) — the cancellation removes duel conditions but the issuance-time effects are not undone.

**Why I didn't fix this**: A correct fix requires:
1. Queue `EventChallengeIssued` in state 01056 right after target is chosen (manual construction matching `stIssueChallenge`'s logic).
2. State 01056_2 then offers move-home (which sets `CHALLENGE_CANCELLED=true` and moves home) vs continue.
3. Continue branch must NOT re-fire `EventChallengeIssued` — meaning the standard challenge state machine path must be modified or skipped, since `stIssueChallenge` is called inside `HIGH_DRAMA_CHALLENGE_ACTION_SETUP_CHALLENGE`.

That's a meaningful refactor with risk of breaking the standard challenge flow's invariants (e.g., `CHALLENGE_CANCELLED` reset at line 704, technique handling, intervention handling). It needs design alignment — not a drive-by fix.

## Concern 2: Performer engagement bypass is consistent with other "special" challenge types

`stIssueChallenge` (StatesTrait.php:719) only engages the challenger when `CHALLENGE_TYPE` is `NORMAL`, `SERVO_SCARPA`, or `TORVO_ESPADA`. `MOVE_ALONG_CHALLENGE_TYPE` (=7) is not in that list, so when defender picks "Continue with Challenge", the performer is never engaged via standard flow — and the action doesn't engage manually either.

Per standard 7th Sea rules, issuing a challenge engages the challenger. So strictly the performer should engage when the challenge proceeds.

But this same bypass exists for `LEGENDARY_REPUTATION_CHALLENGE_TYPE` (Action_01083), `DANIELA_DEITRICH_CHALLENGE_TYPE` (Action_01036), `VERONICAS_GUILLE_CHALLENGE_TYPE` (Action_01033), `JUSTICE_SERVED_COLD_CHALLENGE_TYPE` (Action_02049). It's a systemic pattern — either by design (the action takes the place of the engage cost since the card itself is consumed/used) or a systemic bug. Not appropriate to fix as part of a single-card audit.

## Things that look right

- **Target validation**: `isValidTargetForAbility` rejects own characters and non-co-located characters. ✓
- **Engage on move-home**: `createCardMovingEvent(..., engage=true, ...)` engages the target as required by "may move Home engaged". Already-engaged targets stay engaged. ✓
- **CHOSEN_PERFORMER / CHOSEN_TARGET**: properly set and consumed. ✓
- **Transition ownership**: transitions correctly switch active player between performer's controller and target's controller via `EventTransition.playerId` → `changeActivePlayer` (Theah.php:276). ✓
- **State registrations**: HIGH_DRAMA_PLAYER_TURN_01056 and _2 in States.php, states.inc.php, states.7s5s.php. JS buttons in OnUpdateActionButtons.7s5s.js. ✓
- **Framework cleanup**: Risk-from-hand cleanup (purgatory move, announceAction, pass count reset) handled by FrameworkActionsTrait line 939–974 — confirmed by Amour audit's analysis. The `setUsed`/`resetPlayerPassCount` calls in the move-home branch are redundant but harmless.
- **Challenge stat default**: `CHALLENGE_STAT` is set to `STAT_COMBAT` at start of every high drama player turn (StatesTrait.php:529), so the move-home branch's lack of explicit set is fine.

## What to revisit

- If we ever want Move Along to faithfully trigger "When X issues a challenge" reactions, restructure the action so the challenge-issued event fires before the move-home option, and the move-home branch sets `CHALLENGE_CANCELLED` instead of skipping the standard flow.
- The systemic question of whether special challenge types should engage the challenger is worth a separate design discussion — affects 01036, 01033, 01083, 02049 too.
