# Yield (02020) - Card Text Audit

## Card Text
"City Action: Engage a Melee Weapon or Eisenfaust attachment equipped to your performer and target an opposing non-Leader • They may engage. If they do not, wound them."

## Issues Found & Fixed

### 1. Missing server-side validation in `actFromActionWithId`

**State 02020 handler**: Didn't validate that the target character is not already Engaged. The `getArgsFromAction` and `getPerformers` methods both filter `! $character->Engaged`, so the UI only shows valid targets, but a crafted request could bypass this. Added the Engaged check.

**State 02020_2 handler**: Didn't validate that the chosen attachment has the Melee Weapon or Eisenfaust trait. Args filtered correctly, but the handler accepted any attachment on the performer. Added trait validation.

WHY these matter: BGA games are susceptible to crafted AJAX requests. Server-side validation must independently enforce all constraints, not rely on the client only showing valid options.

### 2. Description text mismatches with card text

- **State 02020 `descriptionMyTurn`**: Changed "choose a non-Leader character to manipulate" → "target an opposing non-Leader character". Card says "target an opposing non-Leader" - "manipulate" isn't in the card text and "opposing" was missing.

- **State 02020_3 `descriptionMyTurn`**: Changed "must choose to Engage or Wound the selected character" → "may engage your character. If not, they will be wounded". This state is presented to the OPPONENT (the transition event uses `$character->ControllerId`). Old wording sounded like actively choosing to wound someone else. New wording matches the card's "They may engage. If they do not, wound them."

### 3. Button label and notification message

- **"Wound" button → "Decline"**: The opponent isn't choosing TO wound - they're declining to engage (wound is a consequence). "Decline" matches "If they do not" from the card text.

- **Notification**: Changed "chose to wound" → "declined to engage" to match the card semantics.

### Things that were correct

- `getPerformers` correctly requires a Melee Weapon or Eisenfaust attachment on the performer
- Opposing non-Leader + not-Engaged filter on target selection is correct
- State flow: pick target → pick attachment → opponent decides is a valid ordering
- Attachment engagement event fires correctly
- Wound event fires with correct parameters
- State 02020_2 description about choosing a Melee Weapon or Eisenfaust attachment is accurate
- JS entering/leaving states correctly highlight/unhighlight performer and character

## Pattern note

State 02020_3 is an `ACTIVE_PLAYER` state where the OPPONENT becomes active (via `createTransitionEvent` with `$character->ControllerId`). This is the standard pattern for opponent-choice effects in this codebase.
