# Vittoria Anselmo (_01014) Audit

## Card Text
> Reaction: When an opponent targets Vittoria, you may put a Thug from your hand into play at this location ignoring all costs • Then, the opponent targets your Thug at this location instead. If your Thug was targeted this way, you may move Vittoria Home.

## Architecture

Complex three-step reaction in `Reaction_01014.php`. The reaction intercepts six event types (Engaged, Engarded, CardMoving, CharacterBeingWounded, CharacterBeingHealed, ChallengeIssued) and uses saved event cloning + re-queuing to redirect targeting. Three boolean flags (`inHandThug`, `inPlayThug`, `moveHome`) drive a multi-stage `performReaction` flow:

1. **inHandThug**: Optionally put a Thug from hand into play via `EventCharacterMustered`
2. **inPlayThug**: Select a Thug at the location to become the new target; validates via `IAbilityThatTargetsCharacters::isValidTargetForAbility`
3. **moveHome**: Optionally move Vittoria Home

## Bug Found & Fixed

**The `moveHome` prompt appeared even when the Thug was NOT successfully targeted.** The card text is conditional: "If your Thug was targeted this way, you may move Vittoria Home." But the old code unconditionally set `moveHome = true` after step 2, regardless of whether:
- The ability validated the Thug as a valid target (it might not be — e.g. ability requires specific traits)
- The ability could even be loaded (edge case: source card removed between event interception and reaction resolution)

When `isValidTargetForAbility` returned false, the code called `cancelEvents()` (correct) but then still set `moveHome = true` and queued a transition (incorrect). Same issue if `loadAbility()` returned null — no explicit handling, fell through to `moveHome = true`.

**Fix**: Added a `$thugWasTargeted` flag. Only set `moveHome = true` and queue the transition when the thug was actually targeted. On the cancel/null paths, mark the reaction as used and end.

## Things That Are Correct

- "Ignoring all costs" is implicitly handled by using `createCharacterMusteredEvent` directly (bypasses normal mustering cost checks)
- Crew cap limit (`Reaction_CrewCapLimit`) still fires on the muster event, which is correct — crew cap is a game rule, not a cost
- `cancelEvents()` unconditionally sets `CHALLENGE_CANCELLED = true` — looks sloppy but is safe because the challenge flow resets it to false before checking
- Decline flows are correct: declining at `inHandThug` still checks for in-play Thugs; declining at `inPlayThug` releases the original event targeting Vittoria with `skipNextEvent` to prevent re-trigger
- `skipNextEvent` mechanism correctly prevents the re-released event from triggering the reaction again
- Event cloning with `unset($event->theah)` prevents serialization issues while preserving event data
