# You Cheated! (_02041) — Scoundrel Maneuver Implementation

## Card Text
**Scoundrel Maneuver:** This duel becomes a duel of [Finesse] for the remainder of the duel.

## Implementation

Simple auto-resolving maneuver. No custom state, no player choices beyond selecting the maneuver.

### Pattern
Follows `Maneuver_01108a` for the hardcoded Scoundrel trait gate and `Maneuver_02009` for the overall maneuver structure. The effect itself is unique — first maneuver in the codebase that changes `CHALLENGE_STAT` mid-duel.

### Key Decisions

**WHY `globals->set` directly instead of an event:** There's no `EventDuelStatChanged` or factory helper for stat changes. Every other place that sets `CHALLENGE_STAT` does it via `globals->set()` directly (challenge actions in `Action_01073`, `Action_01198`, `Action_02028`, framework default in `FrameworkActionsTrait`). Creating a new event type for a single card would be over-engineering. If more cards need this later, an event could be extracted.

**WHY "remainder of the duel" needs no special tracking:** `CHALLENGE_STAT` is set once and persists until `stDuelEnd` calls `globals->delete(Game::CHALLENGE_STAT)`. So setting it mid-duel naturally means it lasts "for the remainder of the duel" with no cleanup needed.

**WHY hardcoded "Scoundrel" instead of parameterized trait:** Only one maneuver on this card, only one trait to check. No reason to add constructor params like `Maneuver_02009` does. If a future card reuses this exact effect with a different trait, it could be refactored then.

**WHY no `EventManeuverCanceled` handler:** The effect writes directly to a global (`CHALLENGE_STAT`) and keeps no local state (no `$IsActive` flag like `Maneuver_02039`). If the maneuver is canceled, there's nothing to roll back — the global wasn't set yet. Contrast with `Maneuver_02039` which sets `$IsActive = true` on resolve and must reset it on cancel. Comment added above `handleEvent` to make this explicit.

## Bug Fix: Restricted Hostilities Ignoring CHALLENGE_STAT

Found during testing. `stDuelEndOfRound` in `StatesTrait.php` had a pre-existing bug where `$stat` was hardcoded to `$adversary->ModifiedCombat` on line 1335 *before* the `$threat > $stat` comparison. The switch that reads `CHALLENGE_STAT` and picks the correct stat was *inside* the `if ($threat > $stat)` block — so it was gated by the wrong stat value.

Scenario: adversary has Combat 3, Finesse 2. Duel switched to Finesse via You Cheated. Player has 3 threat at end of round. Old code: `$stat = ModifiedCombat = 3`, `3 > 3 = false`, switch never entered, player takes 3 wounds. Should have been: `$stat = ModifiedFinesse = 2`, `3 > 2 = true`, wounds capped at 2.

**WHY this was never caught before:** No card in the codebase changed `CHALLENGE_STAT` mid-duel until _02041. When `CHALLENGE_STAT` was set pre-duel (e.g. Finesse challenge from Action_01073), the bug still technically existed but would only manifest if the adversary's Finesse was lower than their Combat and threat fell between the two values — a narrow window that apparently hadn't been hit or reported.

Fix: moved the stat lookup *before* the comparison using a `match` expression on `CHALLENGE_STAT`. The switch inside the `if` block now only appends reason text; `$stat` is already correct.
