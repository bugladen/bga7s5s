# Card Text Audit: Nazem ibn Umur (01119)

## Card Text

> Nazem gains +1 [inf] for each engaged enemy character at his location.
>
> When Nazem issues a challenge to an enemy character, if they refuse, engage them.

## Issues Found and Fixed

### 1. updateInfluence passed raw count as NewInfluence

The `updateInfluence` method was passing `$count` (number of engaged enemies) directly as the `NewInfluence` parameter to `EventCharacterInfluenceModified`. The EventHub sets `ModifiedInfluence = max(0, event->NewInfluence)`, so this would overwrite any attachment bonuses.

With Nazem's base influence of 0 and no current attachments adding influence, this happened to produce the right answer, but it was fundamentally wrong.

**Fix:** Added `$EngagedEnemyBonus` tracking field. New influence is now calculated as `ModifiedInfluence - EngagedEnemyBonus + count`. This preserves attachment modifiers and other external influence modifications while swapping out only Nazem's engaged-enemy contribution.

**WHY a tracking field instead of recalculating from base + attachments:** `ModifiedInfluence` is a single number reflecting ALL modifications (base, attachments, OTHER cards' effects like Épée Sanglante). There's no way to separate other cards' contributions without iterating every possible source. The tracking field lets us subtract our previous contribution and add the new one.

### 2. Move-FROM didn't subtract the leaving character

`EventCardMoved` has `runEventHubAfterCards = true`. When another character leaves Nazem's location, `getOpposingEngagedCharacterCount` still sees them at the old location. If the leaving character was an engaged enemy, the count was 1 too high.

**Fix:** Check if the moving character is an engaged enemy, subtract 1 if so.

### 3. Move-TO didn't add the incoming character

Same timing issue in reverse. When an already-engaged enemy arrives at Nazem's location, they aren't counted because they haven't moved yet. Additionally, the EventHub directly sets `$card->Engaged = true` on move (line 610 of EventHub.php) WITHOUT firing an `EventCardEngaged` event, so there's no follow-up correction.

**Fix:** Check if the incoming character is (or will be) an engaged enemy (`$movedCharacter->Engaged || $event->engage`), add 1 if so.

### 4. Destroyed character still counted

`EventCharacterDestroyed` also has `runEventHubAfterCards = true`. An engaged enemy being destroyed was still counted in the influence calculation.

**Fix:** Check if the destroyed character is an engaged enemy, subtract 1 if so.

### 5. Wrong player name in challenge-rejected notification

The notification said "${player_name} has rejected a challenge" but `player_name` was set to Nazem's controller (`$this->ControllerId`). The player who rejected is the TARGET's controller.

**Fix:** Changed to `$character->ControllerId` (the target who rejected).

### 6. Added null checks

`getCharacterById` returns `?Character`. The EventCardEngaged/EventCardEngarded handlers accessed properties without null checks (EventCardEngaged can fire for non-character cards like attachments). Added `$character &&` guards throughout.

### 7. Player Home false-match bug

`Game::LOCATION_PLAYER_HOME = 'Player Home'` is the same string for all players. When Nazem is at Player Home and an opponent's character moves from/to their own Player Home, `$event->toLocation == $this->Location` matches even though they're at different physical locations.

**Fix:** Added guards to all handlers that compare locations:
- **Move-TO/FROM handlers:** Skip if the location is Player Home AND the moved character's `ControllerId` differs from Nazem's. Used the negated guard pattern since the moved character lookup was already needed for the engaged-enemy offset.
- **Engaged/Engarded/Destroyed handlers:** Added `$this->Location != Game::LOCATION_PLAYER_HOME` to the condition. These handlers only care about enemy characters, and an enemy at "Player Home" is always at THEIR home, never Nazem's.

## Design Notes

- The `$EngagedEnemyBonus` field is serialized/deserialized by PHP's native `serialize()` since cards are stored in the DB that way (confirmed in `DB.php`). For existing games where _01119 was serialized before this change, the field initializes to 0 on deserialization (PHP default value). This could cause one incorrect influence update if there were already engaged enemies, but self-corrects on the next recalculation.
- The `queueEvent()` method already calls `eventCheck()` internally (checked in `Theah.php` line 194). Some other cards (e.g., `_01120`) call `eventCheck` separately before `queueEvent`, which results in double `eventCheck` processing. _01119 correctly only calls `queueEvent`, which is the cleaner pattern.
- `EventCardMoved` engage behavior: the EventHub sets `Engaged = true` directly without firing `EventCardEngaged`. This is why the move-TO handler must account for incoming engaged characters — there's no follow-up event to catch it.
