# Kaspar clone `_01035v2`

User asked to clone `_01035` (Kaspar Dietrich), its composites, states, and supporting code into `_01035v2`. Not a rules change. Original Eisen starter stays `01035`.

## Why a separate recruit type

`KASPAR_RECRUIT_TYPE` (1) is what the pay-for-mercenary Back button keys on (`backKaspar` / `backKasparRecruit` → original 01035_4 / 01035_3). Sharing that constant would send a v2 recruit's Back into the original card's states. `KASPAR_V2_RECRUIT_TYPE` = 4. Anything that is not NORMAL or SILVER_TONGUE already skips the basic Parley gate and the engage-on-parley, so 4 behaves like 1 in `actHighDramaRecruitActionMercenaryChosen` without a new branch there. Added 4 to that test's type list so a later "only these two types" cleanup does not drop v2.

## Why the crew-cap warning was not copied as a new check

`OnUpdateActionButtons.js` uses `action.id.includes('Action_01035')`. Owner ids look like `{cardId}_Action_01035v2`, so the existing check already matches the clone. Tightening it to an exact class name would silently drop the warning.

## State ids

`40103520` / `40103522` / `40103523` / `40103524`. `4010352`–`4010354` are the original substates. Transition key on the High Drama event state is `01035v2`.

## Not cloned

Starter decks, `KASPARS_OCCUPATION` (that is scheme 02014, not this leader), name-match comments on 04015. Printed name, text, stats, and `01035.jpg` stay identical so it is the same card with a new class id (`01035v2` in a deck JSON).

## City Reaction instead of the standing +2

Printed v2 text is **City Reaction: When Kaspar parleys • He gains +2 Influence.** The standing `getParleyDiscount += 2` is gone. Original `_01035` is untouched.

The +2 is still a parley discount, not a chip change. Influence already reduces recruit cost (`Character::getParleyDiscount` adds `ModifiedInfluence`). A permanent `createCharacterInfluenceModifiedEvent` would move the chip, pressures, and the victory total, and would stack if the reaction reset every dusk. That is not what the old constant did.

WHY a flag instead of writing `Game::DISCOUNT` inside `performReaction`: `stRecruitComputeDiscount` runs after the recruit events state and overwrites the global from `getParleyDiscount`. The accept arms `Reaction_01035v2::$ParleyBonusArmed`. `_01035v2::getParleyDiscount` adds 2 only when that flag is set, the performer is Kaspar, he is parleying, and `cardInCity`. Home parleys keep base Influence only.

WHY `EventEnteringPayState` + `PAY_STATE_RECRUIT_MERCENARY`: there is no parley event. Normal recruit already queues EnteringPayState, then drains reactions, then recomputes the discount. Gates: `isAvailable`, in the city, `playerId` is his controller, `CHOSEN_PERFORMER` is him, `PERFORMER_PARLEYED`, mercenary is a negotiable `CityCharacter`. Engaged is fine — his City Action engages him before the parley choice. Once per day via `setUsed`. Pass does not. `EventActionResolved` / `EventPlayerTurnEnd` for his controller clear the flag so a later parley the same day does not keep the +2 after the recruit is over. Public flag because the card is serialized across the playerReaction request.

WHY his own parley no longer jumps straight to pay: `01035v2_4` "parleyChosen" now goes to `HIGH_DRAMA_RECRUIT_ACTION_CHOOSE_MERCENARY_EVENTS`, and the yes branch queues EnteringPayState and sets `PERFORMER_PARLEYED`. Discount stays 0 until the recompute, so the reaction can change it. "noParley" still goes straight to pay. Setting `PERFORMER_PARLEYED` does not double-engage: engage-on-parley is only `NORMAL_RECRUIT_TYPE` inside mercenary-chosen, which this path never enters. Back is still `backKasparV2`, not undo-engage, so the flag will not un-engage him. The pay step will also log the generic "chose to Parley" line. Redundant with his own notify. Left it.

Zombie on `highDramaPhase01035v2_4` used to `nextState("pass")`, which is not a transition on that state. It now calls `actFromCardWithId(0)` (No Parley) so it does not open the reaction.

## Bonus stuck into the next turn

`setUsed` writes the whole card, including `ParleyBonusArmed = true`. The clear on `EventActionResolved` / `EventPlayerTurnEnd` only flipped the in-memory field. Next request loaded the row still armed, the reaction was already Used so it did not ask again, and `getParleyDiscount` still added 2. Same shape as Yevgeni: set `$owner->IsUpdated = true` so `runEvents` flushes the clear. Only when the flag was actually set, so unrelated resolves do not rewrite Kaspar.
