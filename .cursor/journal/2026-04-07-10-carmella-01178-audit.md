# Carmella Vanessa Slavaggi (01178) Audit

## Card Text
> Negotiable (You may parley when paying for this card.)
> Once per Day, Carmella may issue a challenge or intervene in one even while engaged.

## Verdict: One Bug — Intervention Event Ordering

### What's correct
- `$this->Negotiable = true` handles the Negotiable keyword
- `canChallenge()` / `canIntervene()` share identical logic: `!$this->Engaged || !$this->AbilityUsed` — allows the action when not engaged (normal behavior) or when engaged but the once-per-day ability hasn't been used yet
- `AbilityUsed` is shared between challenge and intervene (card says "challenge **or** intervene" — one shot per day total)
- `EventDuskEndOfDay` resets `AbilityUsed` — correct "once per Day"
- Three call sites (ArgumentsTrait, FrameworkActionsTrait, Theah) all special-case `instanceof _01178` to skip the normal `$character->Engaged` gate, relying on `canChallenge()`/`canIntervene()` to handle it

### The bug: intervention event ordering burns the ability even when unenganged

**Challenge path** (StatesTrait::stIssueChallenge):
1. `EventChallengeIssued` queued
2. `EventCardEngaged` queued

When _01178 handles `EventChallengeIssued`, `$this->Engaged` reflects the **pre-challenge** state. If she was already engaged, AbilityUsed is set. If not, it isn't. ✅

**Intervention path** (FrameworkActionsTrait::actHighDramaChallengeActionIntervene):
1. `EventCardEngaged` queued  ← fires first
2. `EventCharacterIntervened` queued

When _01178 handles `EventCharacterIntervened`, `$this->Engaged` is **always true** because the engage event already processed. So AbilityUsed gets set every time she intervenes, even if she was free (not engaged) beforehand. ❌

### Fix
Swapped the queue order so `EventCharacterIntervened` is queued before `EventCardEngaged`, matching the challenge pattern. Verified no other card depends on the old ordering:
- Rena (01040): `engageRequired = false` for her, so no engage event is queued at all
- Odette (01062): The `eventCheck` call happens before *any* event is queued, so unaffected
- Vladislav (01188): His `EventCharacterIntervened` handler checks `newTargetId` only, no `Engaged` dependency
- Reactions 01100, 01065, 01023: All use `eventCheck` (runs before queueing) or check fields unrelated to engagement state

### WHY this ordering approach
An alternative was adding a `$WasEngagedBeforeAction` flag to _01178 and setting it from FrameworkActionsTrait before events queue. That introduces tight coupling between the framework code and a specific card class. The event-reordering fix is cleaner — it makes intervention consistent with the challenge path and doesn't require any card-specific state tracking beyond what already exists.

## Ability Used Chip (UI indicator)

Added a visual chip on Carmella's card (like Maryam Benu Pleroma) showing when her once-per-day ability has been consumed. Uses the conditions system for persistence/page-refresh support alongside the existing `AbilityUsed` boolean for game logic.

### WHY keep both AbilityUsed and the condition
The `AbilityUsed` boolean is serialized as part of the card data in ongoing games. Replacing it entirely with a condition could cause deserialization issues for in-progress games. Keeping both is redundant but safe — `AbilityUsed` drives game logic, the condition drives the UI chip. They're kept in sync by `setAbilityUsed()` / `clearAbilityUsed()` helpers.

### Pattern followed
Exact same pattern as Maryam (_01186):
- Game constant → condition on card → notifications → JS chip rendering on condition check + notification handlers
- Chip uses cropped card art in a circle with orangered border
