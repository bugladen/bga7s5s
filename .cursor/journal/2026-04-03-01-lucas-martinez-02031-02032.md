# Lucas Martinez "Doomed" (_02031) / "Damned" (_02032) Implementation

## What Was Done

Implemented the linked pair of Lucas Martinez cards. These form a transform mechanic: when Doomed enters play he stages Damned in the Locker, and when Doomed dies, Damned rises from the Locker at the same location. Damned self-destructs at Dawn and offers a Reaction to recover a Risk.

### Files Modified
- `modules/php/cards/tac/_02031.php` -- added `handleEvent` with two Forced triggers
- `modules/php/cards/tac/_02032.php` -- added `IHasReactions`, `ReactionTrait`, wired `Reaction_02032`, added Dawn destroy handler

### File Created
- `modules/php/cards/tac/reactions/Reaction_02032.php` -- "Put Risk in Hand" / "Pass" reaction

## Key Design Decisions

### _02031 muster handler creates _02032 at runtime

WHY: _02032 never exists in a player's deck or collection. It's conjured "from out of play" by _02031. We use `createCardInLocation('02032', lockerName, ...)` to insert a DB row and instantiate the PHP object, then add it to the world and queue `EventCardSentToLocker` for the notification pipeline.

Every time _02031 musters, a new _02032 is created. If _02031 musters multiple times (through game effects bringing it back), there could be multiple _02032 instances in the locker. The destroy handler only grabs the first one found. This is acceptable since the card text doesn't limit creation count.

### _02031 destroy handler uses `$this->Location` for "that location"

WHY: When `EventCharacterDestroyed` fires, EventHub processes first -- it moves _02031 to the locker and re-instantiates a fresh _02031 object. BUT the `foreach` in `runEvents` iterates over a PHP array snapshot taken at loop start, so the OLD _02031 object (with its pre-destruction `Location` still intact) is the one whose `handleEvent` fires. This means `$this->Location` is the city location where Doomed was stationed, which is exactly "that location" from the card text.

This is a subtle but reliable PHP behavior. The new _02031 object (in the locker) is in `$theah->cards` for future event cycles, but the foreach for the current event uses the snapshot. If this ever causes confusion, the journal entry right here explains why.

### _02032 Dawn destroy has no location guard

WHY: Eddie confirmed the destroy fires regardless of where Damned is. Cards in the Locker aren't loaded by `buildCity`, so they don't receive `EventPhaseDawnBeginning`. If _02032 is receiving the event at all, it's in play and should be destroyed. No city-location check needed.

### _02032's Reaction handles its own muster

The Reaction_02032 listens for `EventCharacterMustered` where the characterId matches the owning card (_02032). When _02031's destroy handler queues `EventCharacterMustered` for _02032, it adds _02032 to the world first. By the time runEvents processes the muster event in the next while-loop iteration, _02032 is in `$theah->cards` and its Reaction receives the event.

The reaction checks for any Risk card in the player's locker (`instanceof Risk`). If found, it offers a button per Risk in the locker (not a generic single button) plus a "Pass" button. On confirm, it queues `EventCardRemovedFromLocker` then `EventCardAddedToHandEvent` for the chosen Risk. The notify message includes the Risk's inject code so the name shows in the game log.

### Corrections made during review

1. **Reaction buttons list individual Risks.** Initial implementation had a single generic "Put Risk in Hand" button. Eddie pointed out the buttons should list each Risk in the locker individually (button text: "Put in Hand: {RiskName}", reaction id: "putRisk-{cardId}"). `performReaction` extracts the card ID from the reaction string.

2. **Risk must be removed from the locker.** Initial implementation only queued `EventCardAddedToHand`. Eddie pointed out we also need `EventCardRemovedFromLocker` queued before the hand event so the card properly leaves the locker.

3. **Notify must include the Risk name.** Initial notify message was generic. Eddie pointed out we need to load the Risk via `getCardObjectFromDb` and include its `getInjectCode()` as `${risk_inject_code}` in the message.

## Potential Edge Cases

- Multiple _02032 instances in locker if _02031 musters repeatedly -- only the first is used for each destruction
- If no _02032 exists in the locker when _02031 is destroyed (shouldn't happen in normal flow), the handler silently does nothing
- If no Risk exists in the locker when _02032 musters, the Reaction doesn't trigger at all (no transition event queued)
