## Torvo Espada (02034) implementation

**Why `TORVO_ESPADA_CHALLENGE_TYPE` (15) instead of reusing `VALERI_MIKHAILOV_CHALLENGE_TYPE`:** Same intervene-blocking behavior, but `Theah::interventionCheck` throws a user-visible string; Valeri’s message would be wrong. Also `stIssueChallenge` must **engage the challenger** for Torvo’s flow (opponent accepts and issues to Torvo). Valeri’s type skips the NORMAL engage block because Valeri’s action already moved/engaged him; Torvo’s challenger still needs the same engage path as NORMAL, so `TORVO_ESPADA` was folded into the engage condition alongside NORMAL and SERVO_SCARPA.

**Flow:** Action step 1 mirrors Valeri: queue `TransitionEvent` to hand off to opponent (`02034_2`), then `nextState('targetChosen')` → EVENTS so the transition runs from the events state machine (not a direct jump to the sub-state). Step 2: accept queues `02034_3` → shared technique-available state; decline queues `CardDrawn` for Torvo’s controller.

**Edge choices:** Targets must be unengaged and `ModifiedCombat >= 2` at Torvo’s location (tac convention). Zombie on opponent step uses empty transition like 02020_3 (decline path).

**PHP not in PATH** on the agent shell—could not run `php -l`; IDE linter reported no issues.

**Dashed Parry / Riposte:** Eddie wants Torvo’s technique to follow the global `EventHub` rule: if all played combat cards have dashed Parry (or dashed Riposte), technique Parry (or Riposte) is not applied—no bypass flags on `EventDuelCalculateTechniqueValues`.

**Technique availability:** `Technique_02034::isAvailableToPlayer` requires `Game::IN_DUEL` so Parry/Riposte only show as selectable during an active duel (same pattern as `Technique_PlusOneParry`), not during the pre-duel challenge / technique-pick flow where those stats do not apply.
