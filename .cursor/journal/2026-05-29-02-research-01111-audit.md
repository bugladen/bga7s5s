# Research (01111) Audit

## Card Text
> **Action:** Choose three cards with different names in your discard pile • An opponent of your choice puts one of them into your hand. Send this card to The Locker.

Castille Risk, 0 wealth, 0/2/3 R/P/T (Riposte dashed). Traits: Discovery, Scholarship.

## Component Inventory
- `modules/php/cards/_7s5s/_01111.php` — Risk + IHasActions; handles "send to Locker" on play.
- `modules/php/cards/_7s5s/actions/Action_01111.php` — extends `RiskAction`. Three-stage flow.
- `modules/php/States/_7s5s/State_highDramaPhase01111.php` — pick 3 cards from your discard.
- `modules/php/States/_7s5s/State_highDramaPhase01111_2.php` — pick an opponent.
- `modules/php/States/_7s5s/State_highDramaPhase01111_3.php` — opponent picks 1 of the 3.
- `states.inc.php` — `"01111"` and `"01111_3"` registered under `HIGH_DRAMA_PLAYER_TURN_EVENTS` transitions. (No `"01111_2"` entry needed — that state is reached via `""` from 01111, not via a transition event.)
- `modules/js/OnEnteringState.7s5s.js`, `OnUpdateActionButtons.7s5s.js`, `OnLeavingState.7s5s.js`, `EventHandlers.js` — frontend wired up.

## Things That Look Right
- **Class hierarchy / performer scope.** Plain `Action:` (not `City Action:`) → `RiskAction` is correct; `RiskAction::getPerformersForAction` returns `getCharactersInPlayByPlayerId` which includes both home and city characters. ✓
- **Locker handler in `_01111.php`.** Filters on `EventCardDiscardedFromHand && cardId == $this->Id && $event->AsPlayed`. The `AsPlayed=true` filter correctly excludes the cases where this Risk is used as a combat card or as payment (where `AsPlayed=false`). Mirrors the `_01139` pattern (no `goToLocker` flag is needed here because there's no Maneuver). ✓
- **Different-names check.** Compares by `$card->Name` (the printed card name), which is the right notion of "different names" — Cesca/Katain copy semantics aside, the Name property is what's printed on the card face. ✓
- **Opponent selection.** State 01111_2 builds opponent list excluding the active player; `actFromActionWithId` re-validates `id != activePlayerId` and `isset($players[$id])`. ✓
- **Active player handoff.** State 01111_2 fires `createTransitionEvent($opponentId, …, "01111_3", …)`, which `Theah::runEvents` translates into `changeActivePlayer($opponentId)` + `nextState("01111_3")`. The opponent becomes active in state 01111_3. ✓
- **Discard pile reference.** In 01111_3, `$owner->ControllerId` still resolves to the original Risk player (the Risk card's controller doesn't change), so the opponent is correctly picking from the *Risk player's* discard, not their own. ✓
- **Card returned to Risk player's hand.** `createCardAddedToHandEvent($owner->ControllerId, $id)` adds to the original player, not the opponent. ✓
- **`createActionResolvedEvent`** fired at the end of 01111_3 (pre-commit hook requirement met). ✓
- **State ID encoding.** `401111`, `4011112`, `4011113` follow the `4` + cardId + suffix convention.  ✓
- **Typed parameters** throughout. ✓

## Issues Found

### 1. (bug) State 01111_3 doesn't validate the chosen card is one of the three picked
`Action_01111::actFromActionWithId` for state `01111_3` (lines 149–180) checks only:
- card exists, and
- card is in the Risk player's discard pile.

It never verifies that `$id` is one of the three IDs the active player saved into `CHOSEN_CARD` back in state 01111. A misbehaving client could submit *any* card from the Risk player's discard pile and the server would accept it. The UI restricts the choice (it only renders the three saved cards), but server-side enforcement is missing.

Fix: load `$game->globals->get(Game::CHOSEN_CARD)` and reject if `$id` isn't in that array.

### 2. (deprecated API) `getActivePlayerName()` in notification
Line 166:
```php
"player_name" => $game->getActivePlayerName(),
```
Per memory, `getActivePlayerName` is deprecated and can return the wrong player in handoff contexts. Here it happens to return the opponent (the chooser), which *is* the intended speaker for "${player_name} chooses … to research" — but the API is still deprecated. Replace with `$game->getPlayerNameById($game->getActivePlayerId())`, or better, use the saved `CHOSEN_OPPONENT` id directly for clarity.

### 3. (deprecated API) `\BgaUserException`
All five `throw new \BgaUserException(...)` calls in `Action_01111.php` should be `throw new \Bga\GameFramework\UserException(...)` (with a `use` statement at the top). Per memory, `\BgaUserException` is deprecated.

### 4. (code smell) `CHOSEN_CARD` stores an array of three IDs
Line 118 does `$game->globals->set(Game::CHOSEN_CARD, $ids)`. Every other use of `CHOSEN_CARD` in the codebase (FrameworkActionsTrait, StatesTrait, ArgumentsTrait — ~30 sites) treats it as a single `int`. There's no `CHOSEN_CARDS` constant, so this is a one-off overload. It works because nothing in the intermediate EVENTS pass reads `CHOSEN_CARD`, but it's a footgun if a future event handler ever does.

Two options: (a) introduce a card-local global key (other multi-stage cards do this); or (b) accept the abuse and leave a `// WHY:` comment explaining that CHOSEN_CARD is used as an array here. Lean toward (a).

### 5. (UX question) Notification message attributes the choice to the opponent
"${player_name} chooses ${card_inject_code} to research." With `getActivePlayerName()`, this resolves to the *opponent*. Reading it cold, "chooses X to research" sounds like the opponent is the one researching. The Risk player is the recipient. Consider rephrasing for clarity, e.g.:
> `${opponent_name} chooses ${card_inject_code} for ${owner_name} to research.`

Minor; raise with the user.

### 6. (precondition gap, possibly intentional) No `isAvailableToPlayer` check that the discard has ≥3 distinct-named cards
If your discard pile has fewer than 3 cards with distinct names, the Action is still selectable, but `actFromActionWithIds` will reject every submission and the active player is effectively stuck in state 01111 (no pass button visible in the JS). RiskAction doesn't supply a pass path here, so the player has to choose 3 valid cards or… nothing.

Whether to fix depends on rules intent: BGA tournament rules sometimes say "you can choose to take an action you can't fulfill" as a chicken move, but more commonly availability requires fulfillability. Worth confirming with the user / rulebook.

## Fixes Applied (this session)

User approved fixing #1, #2, #3, #5, #6. Left #4 (CHOSEN_CARD-as-array) as-is by design.

- **#1 (server-side card validation)**: In `actFromActionWithId` state `01111_3`, added an `in_array($id, $chosenIds)` check against `Game::CHOSEN_CARD` before any other validation. Now the opponent can only submit one of the three IDs the active player saved.
- **#2 (`getActivePlayerName` deprecated)**: Notification now resolves names via `getPlayerNameById($game->getActivePlayerId())` (the opponent doing the choosing) and `getPlayerNameById($owner->ControllerId)` (the original Risk player).
- **#3 (`\BgaUserException` deprecated)**: Added `use Bga\GameFramework\UserException;` and replaced all five `throw new \BgaUserException(...)` sites with `UserException`.
- **#5 (notification clarity)**: Rephrased to `"${opponent_name} chooses ${card_inject_code} for ${player_name} to research."` — explicit about who's choosing and who's researching.
- **#6 (precondition)**: Added `Action_01111::isAvailableToPlayer` override that walks the Risk player's discard pile, builds a set of distinct `Name`s, and returns false if `< 3` distinct names exist. This blocks the action from being selectable in cases where it couldn't be fulfilled.
  - WHY this layer: doing the check at availability rather than as a `UserException` in `actFromActionWithIds` means the action button is suppressed when unusable, which prevents the "stuck in state 01111 with no pass" failure mode I called out in #6.
  - Used `$theah->game->getPlayerDiscardDeckName(...)` — `Theah::$game` is public, and `Theah::getCardObjectsAtLocation` is the discard-iteration primitive used elsewhere in this same class (`getArgsFromAction`).

## Risk Assessment
- Issue #1 (server-side card validation): real, low-frequency exploit but should be fixed.
- Issues #2 and #3: pure deprecation cleanup, no behavior change.
- Issue #4: stylistic; works as written.
- Issues #5 and #6: design questions, not bugs.

No issues touch the duel-card path or the Locker handler; those look correct.

## WHY for future-me
The `"01111_2"` transition is intentionally NOT in `states.inc.php`. We enter 01111_2 via the empty transition from 01111 (`"" => 01111_2`), not via a transition event. Only state names that need to be reachable from `HIGH_DRAMA_PLAYER_TURN_EVENTS` via a transition-event payload appear in that map — and that's only 01111 (the entry) and 01111_3 (the handoff to the opponent). Don't "fix" this by adding a 01111_2 entry; nothing would dispatch to it.

The Locker handler doesn't need a `goToLocker` flag (unlike `_01139`) because Research has no Maneuver — the only `AsPlayed=true` discard for this card is the Action play.
