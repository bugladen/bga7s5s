# Marooned (01148) Audit

## Card Text
"Add a Renown to [The City Docks] and [The Grand Bazaar]."
"City Action: Target a Mercenary opposing your performer. You may discard any number of cards. Engage or wound that character for each card discarded this way."

## What I Found

The state machine for this card is a multi-step loop, which took careful tracing to understand:

- 01148: Choose target mercenary
- 01148_2 (game): Check if player has cards in hand AND target is still alive
- 01148_3: Discard a card or click Finished
- 01148_4: Choose Engage or Wound for that discard

The loop works via transition events routed through the EVENTS state in states.inc.php:
- "01148_3" → 01148_4 (after discard, go to engage/wound)
- "01148_4" → 01148_2 (after engage/wound, loop back to check)

This naming is confusing because the transition name "01148_3" doesn't go BACK to state 3 - it goes to state 4. The suffix names the SOURCE state, not the destination. Had to read states.inc.php carefully to understand this.

## Bugs Fixed

### 1. Missing actionResolvedEvent on "Finished" (Critical)
When player clicks "Finished" (id=0) in state 01148_3, the code just called nextState() without queuing an actionResolvedEvent. The cancel path in 01148_2 correctly fires this event, but the voluntary "Finished" path did not. This means reactions listening for EventActionResolved (like 01089, 01116b) wouldn't trigger when the player finished discarding.

### 2. Missing Mercenary trait validation in isValidTargetForAbility (Minor)
The available targets are pre-filtered by getOpposingMercenariesAtLocation on both the availability check and the args, but the server-side validation in isValidTargetForAbility didn't verify the Mercenary trait. Added hasTrait("Mercenary") check for consistency with other cards (01036, 01051).

## Scheme Resolve
Adds renown to Docks and Grand Bazaar. Straightforward and correct.
