# Maneuver_01110 (Nothing Personal) Audit

## Card Text
> **Maneuver:** Wound the adversary. If your participant has 3 [Combat] or more, this location becomes uncontrolled unless they take another wound.

## Audit Findings

The intended flow:
1. Adversary takes 1 wound (always).
2. If actor has Combat >= 3, the adversary's controller chooses: take another wound, OR allow this location to become uncontrolled.

Implementation already had the right shape (handleEvent queues the wound + a transition to `DUEL_RESOLVE_MANEUVER_01110` when actor's `ModifiedCombat >= 3`; UI presents two buttons in `OnUpdateActionButtons.7s5s.js`; state file transitions for `$adversary->ControllerId`).

## Bug Fixed

`actFromManeuverWithId` was calling `getDuelOpponentId($owner->ControllerId)`. WHY this is wrong: `getDuelOpponentId` reads from the `duel` table (`challenger_id`/`defender_id`), which stores **character IDs**, not player/controller IDs. Passing a player ID would never match either side, so the function would silently return `challenger_id` regardless of who the actor was — meaning the wrong character could be wounded and the wrong character's location chosen for the "uncontrolled" effect.

`handleEvent` had already been corrected to use `getDuelRoundActor()->Id` (presumably as part of the WIP work that was uncommitted on this file). But `actFromManeuverWithId` still had the old buggy pattern in both id=1 and id=2 branches.

Fix: derive `$actor` via `getDuelRoundActor()` and use `$actor->Id` for the lookup, then resolve the adversary character. Consolidated the lookup at the top of the state branch since both id=1 and id=2 need it.

Also corrected the player_name in the chat notifications: this state runs as the adversary's controller (the one making the choice), so the message should name `$adversary->ControllerId`, not `$owner->ControllerId` (the actor's player). The previous code attributed the choice to the wrong player.

## Things I considered but didn't change

- "this location" — since both combatants in a duel are at the same location, using `$adversary->Location` is fine; it's the duel location.
- Whether to guard against the location being already uncontrolled: not changed. The text doesn't restrict this, and an already-uncontrolled location is a no-op for option 2 — the choice is still meaningful.
- `isAvailableToPlayer` already disables the maneuver if the adversary is in discard/locker (already KO'd). Good.
- The `EventLocationBecomesUncontrolled.playerId` is set to `$owner->ControllerId` (actor's player). This matches the pattern in `Action_01086` (Make Location Uncontrolled).
