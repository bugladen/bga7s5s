# Card _01100 (The Cat's Glass) Audit

Card text: "Reaction: When a character at this location accepts a challenge, engage this card • For the rest of the duel, while the adversary is at this location, they reveal one less card when gambling."

## Audit results

`Reaction_01100` (AttachmentReaction) trigger and effect logic was mostly right:
- Trigger fires on `EventChallengeAccepted` when the owner's attached character is challenger or target at the same location.
- `EventCharacterIntervened` is treated equivalently to ChallengeAccepted (intervention IS acceptance for our purposes).
- `getNumberOfGambleCardsToReveal` returns -1 when actor is the recorded adversary AND the owning character is currently at the same location as the actor. The location check is dynamic, so if either party moves away the effect deactivates correctly. ✓
- `EventDuelEnd` resets `IsActivated` and `AdversaryId`, so the effect is bounded to "the rest of the duel". ✓

## Bugs found and fixed

### Bug 1: `IsActivated` set unconditionally in `handleEvent`

Original code did `$this->IsActivated = true;` inside `handleEvent` BEFORE the player chose Activate/Pass. If the player chose **Pass**, `IsActivated` stayed `true` and the gambling -1 penalty applied to the adversary for the rest of the duel — but the card was never engaged, so the player got the effect for free.

Fix: Moved `$this->IsActivated = true;` to the `'activate'` branch of `performReaction`. `AdversaryId` is still recorded in `handleEvent` (we need to know who the adversary would be in case the player chooses to activate), but the `IsActivated` flag — which is what gates the gambling effect — only flips when the player commits.

WHY: Compare to `Reaction_01047` (Cancel Adversary's Technique) and `Reaction_01116b`, which both follow this same pattern: store target/state data in `handleEvent` so it's available, but only flip the activation flag in `performReaction`'s 'activate' branch. Reaction_01100 was the outlier.

### Bug 2: Missing `setUsed()` call

The pre-commit hook (`.githooks/pre-commit` rule for `extends AttachmentReaction`) requires `$this->setUsed()`. The original file lacked it. Without it, the reaction's `isAvailable()` always returned true, so the reaction could re-trigger on every `EventChallengeAccepted` within the same day. (Within a single duel only one ChallengeAccepted fires, but across multiple duels in a day it would re-arm.)

Fix: Added `$this->setUsed($game->theah, true);` in the 'activate' branch alongside the engage event. `Used` is reset by the parent CardReaction on `EventDuskEndOfDay`, giving the natural once-per-day cadence consistent with the engage-as-cost paradigm.

## Decisions / non-bugs noted

- **Trigger restricted to challenges involving the owner's character.** The text says "when *a* character at this location accepts a challenge," which could be read as ANY character. The implementation only fires when the owner's attached character is the challenger or the target. Kept as-is — "the adversary" only has a coherent meaning if the owner's character is one of the duelists, otherwise the second sentence ("while the adversary is at this location") has no referent.
- **Location check uses owning *character's* location.** Since the card is an attachment, its location tracks the attached character. `getOwningCharacter(...)->Location` is therefore equivalent to "this card's location." If the owner is destroyed mid-duel the attachment goes to discard and the reaction object stops being consulted — no NPE risk in practice.
- `EventDuelEnd` reset is defensive cleanup; it runs even if the reaction never fired this duel, and that's fine.

## Notes for next session

Did not change the engage flow. The `'pass'` branch is intentionally a no-op aside from `nextState`. With the `IsActivated` move, passing now correctly yields no effect at all, which matches the card text where engage and gambling penalty are joined by "•" as a single coupled effect.
