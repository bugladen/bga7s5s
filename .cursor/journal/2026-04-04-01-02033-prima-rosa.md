## _02033 “Prima” Rosa — full implementation

### Why these choices

- **Revelry → Lethal:** Hooked `EventDuelCalculateCombatCardStats` when `actorId` is Rosa and the combat card `hasTrait(clienttranslate('Revelry'))`, then `createGainLethalEvent` — same timing as other combat-card stat modifiers (e.g. Reaction_02017). Added an `explanations[]` line so the duel preview shows why lethal applied.

- **City Action:** `ICityDeckCard` + `!isControlled()` matches “available City Card” usage in Action_01072. Adjacency via `getAdjacentCityLocations($rosa->Location, false)`. Move uses `createCityCardAddedToLocationEvent` (not `createCardMovingEvent`) because city cards use that event in EventHub.

- **Reaction:** `awaitingMoverDiscard` is required when Rosa’s controller == mover’s controller so `getActivePlayerId()` alone cannot distinguish step 1 vs step 2. “Have Them Discard” only appears if mover has ≥1 hand card; if they empty between click and resolve, notify and abort without `setUsed`. `pendingMoverCharacterId != 0` blocks stacking a second trigger while a prompt is open. Dusk clears pending flags in addition to parent `CardReaction` reset.

- **State 402033:** Single-step pick like 02023’s first state; JS reuses `highDramaPhase02023` card-highlight + confirm pattern.

### Follow-up: City Action move

`createCityCardAddedToLocationEvent` only set `Location` + `deck->moveCard` to the new pile but did not match full move semantics Eddie saw in play. Switched to `createCardMovingEvent` → `EventCardMoved` so the deck layer removes the card from the old location (same path as characters). Dropped the extra `message` notify; `cardMoved` from EventHub covers it.
